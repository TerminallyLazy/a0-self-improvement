# Route analysis by declared need and bound candidate search cumulatively

A0 Self-Improvement will keep deterministic aggregation as the mandatory factual foundation, add typed Predict or recursive RLM only through an immutable Analysis Route chosen before semantic output is observed, and treat every model result as a non-authoritative Analysis Proposal. Outcome-aligned GEPA may generate an Improvement Artifact only after explicit admission and within one cumulative, externally enforced Optimization Run Budget; it cannot learn from the Certification Holdout or turn search scores into activation evidence. This favors reproducible authority and bounded spend over count-based routing, silent fallback, surrogate optimization, and library-local budget hints.

## Consequences

- Deterministic analysis owns counts, grouping, windows, joins, validation, evidence-reference checks, budget accounting, and every conclusion expressible from typed evidence. The built-in uncalibrated automatic policy authorizes deterministic analysis and zero external model spend. An explicit operator Model Use Grant may authorize bounded diagnostic model analysis or search, but only an approved Policy Calibration Artifact can make model-backed candidate search promotion-eligible or authorize automatic spend.
- An Analysis Route is `deterministic`, `typed_predict`, or `recursive_rlm`. Routing uses the declared analytical question, Safe Analysis View shape, need for decomposition, processing authority, capability, and reserved budget rather than raw event or Fixture Family counts. The provisional `40/200 events` and `4 families` cutoffs have no authority.
- Typed Predict is permitted only for one bounded structured semantic inference whose complete Safe Analysis View fits the declared direct-input ceiling. Recursive RLM is permitted only when the approved question genuinely requires iterative exploration across multiple bounded aggregate views or allowlisted safe tools. Neither route receives raw prompts, tool arguments or results, secrets, unrestricted trace content, quarantine content, or Certification Holdout content.
- Model output must satisfy a fixed schema, cite existing opaque evidence references, and pass deterministic finiteness, reference, contradiction, and completeness checks. Valid rows remain Analysis Proposals for candidate discovery; they cannot become Outcome Evidence, expected truth, Bucket Validator results, judge calibration, hard vetoes, or promotion authority.
- Every Analysis Attempt records the requested and selected route, selection reason, Analysis Profile, input identity, exact model and source when used, Worker Dependency Profile, reserved and actual budget, invalid or dropped output counts, proposal hashes, terminal state, cleanup, and bounded reasons. Prompts, model reasoning, raw tool traffic, and provider response identifiers are not durable.
- Missing dependencies, model authority, provider capability, safe input, calibration, budget, or valid output makes the requested route unavailable, partial, budget-exhausted, failed, or incompatible. Silent fallback is forbidden. A separately permitted deterministic or heuristic attempt has a new route, run identity, and receipt and never relabels the failed model attempt.
- GEPA admission freezes the incumbent Activation Profile and scope revision, target Artifact Slot, successor shape, Candidate Risk Tier, Candidate Benefit Claim, Execution and Assessment Profiles, outcome-aligned Optimization Metric Profile, family-partitioned training and tuning manifests, replay capability, Worker Dependency Profile, Model Use Grant, and Optimization Run Budget before compilation.
- Candidate generation and GEPA search may use admitted training families and a distinct tuning partition only. Certification Holdout identities and content remain inaccessible until the output artifact is locked. Family overlap, stale or missing authority, contaminated-only support, historical model output as truth, or post-hoc benefit selection denies admission.
- The Optimization Metric Profile may map typed training or tuning Outcome Dimensions and Bucket Validator results to a bounded scalar plus fixed reason-coded feedback aligned with the Candidate Benefit Claim. That scalar exists only to steer search. Individual invalid or unsafe proposals receive the declared failure score and cannot become artifacts; a live-tool, secret, fixture-authority, sandbox, or protected-boundary breach aborts the run.
- Current rule-label agreement GEPA and prompt token-overlap GEPA are surrogate diagnostics, not outcome-optimized self-improvement, and cannot emit promotion-eligible candidates. The exact stable legacy identifiers and compatibility schema are decided by the artifact-schema ticket.
- One Optimization Run Budget covers deterministic preparation, Predict or RLM work, semantic judging, GEPA reflection, task-model evaluation, replay-backed metric calls, compiled-program validation, cache misses, retries, and all prompt components. It includes hard wall-clock deadline; root, submodel, reflection, judge and task-model calls; input/output tokens and bytes; observable cost and reservations; metric invocations; unique variants; cases and Fixture Families; RLM iterations and tool queries; retry attempts; and per-run, per-context, per-provider and host concurrency.
- The single-host Budget Ledger atomically reserves capacity before each external call or metric evaluation and reconciles actual usage afterward. Cache hits remain logical metric invocations and are keyed by the exact program or rule-set digest, case and fixture versions, model revision, Evaluation Envelope, metric profile, and policy; partial, failed, stale, or cross-boundary results are never cached or reused.
- DSPy GEPA `max_metric_calls` is an approximate algorithmic search allowance, not the total spending boundary. DSPy RLM `max_llm_calls` limits recursive sub-LM calls, not root iterations or forced extraction. GEPA `num_threads` is clamped to a pre-reserved aggregate evaluation allowance. All library knobs sit inside the Budget Ledger and killable worker deadline.
- Unknown price or unavailable usage accounting cannot satisfy a monetary cap. A provider-backed call requires a Model Use Grant and either conservative pre-dispatch token/cost reservation with reconcilable usage or an explicit not-applicable local-provider profile. A zero-dollar budget never means unlimited or unknown-cost use.
- Analysis and candidate search execute in fresh, killable plugin-owned processes. Deadline, cancellation, lease loss, fence loss, dependency drift, or budget exhaustion terminates the process after bounded cleanup, discards partial compiled output, and emits only an Optimization Run Receipt. Candidate publication rechecks the lease, fence, dependency profile, grant, and remaining budget in one transaction; late results cannot become discoverable.
- Provider or infrastructure exhaustion is unavailable or stopped and never candidate harm. A candidate-attributable hard-budget violation during authoritative replay remains a hard veto under the Activation Policy. Underpowered or uncalibrated admission remains review-only.
- The model-worker compatibility range is CPython `>=3.12,<3.15`, intersecting Agent Zero's framework runtime with DSPy and GEPA support. Promotion-authoritative work additionally requires a certificate for the exact interpreter, ABI, OS/architecture, Agent Zero build and allowed framework bridge; the initial pinned Docker compatibility target uses the Python 3.12.4 framework runtime, not the Python 3.13 agent-execution runtime.
- The worker uses a generated, hash-complete transitive dependency lock and does not inherit arbitrary `--system-site-packages`. `dspy[deno]==3.3.1` is the sole model-worker root; its resolved closure must contain the expected GEPA version. The redundant direct GEPA root and unused `dspy-cli` runtime dependency are removed; any future CLI tooling uses a separate operator-only environment.
- A Worker Dependency Profile and capability certificate bind the lock digest, trusted package sources and hashes, Python/platform identity, narrow framework bridge, DSPy/GEPA/Deno versions, plugin adapters, and separate behavioral probes for Predict, RLM sandbox lifecycle and limits, outcome GEPA, metering, cancellation, and cleanup. Startup or lifecycle repair may build a staging environment from that lock, but readiness is read-only evidence and becomes unavailable on any drift.
- Acceptance separately proves deterministic and model-route receipts; malformed, fabricated, partial and non-finite model output; holdout and family isolation; outcome-metric behavior; atomic multi-process budget enforcement; unknown-cost denial; deadline/cancellation/fencing with no late candidate; lock and marker tampering; standalone fake-provider behavior; clean pinned Agent Zero compatibility; authorized real-provider behavior; and the exact named live runtime.

## Evidence basis

- DSPy 3.3.1 supports Python `>=3.10,<3.15`, includes Deno as the RLM extra, and already pins `gepa[dspy]==0.1.4`: https://github.com/stanfordnlp/dspy/blob/3.3.1/pyproject.toml
- DSPy RLM 3.3.1 marks the API experimental and defines `max_llm_calls` as the recursive sub-LM-call limit: https://github.com/stanfordnlp/dspy/blob/3.3.1/dspy/predict/rlm.py
- DSPy GEPA 3.3.1 describes its metric-call count as approximate and rejects unsupported `max_reflection_cost`: https://github.com/stanfordnlp/dspy/blob/3.3.1/dspy/teleprompt/gepa/gepa.py
- `dspy-cli` is a separate serving and project-scaffolding tool that requires its own server-oriented dependency set; the plugin does not invoke it: https://pypi.org/project/dspy-cli/0.1.13/
